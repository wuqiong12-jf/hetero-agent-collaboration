## 从源码开始

需要 Node.js 22 或更新版本；Harness 桥接需要 Python 3.10 或更新版本。项目主要在 Windows Codex 桌面环境验证。

```powershell
npm ci
npm run package:plugin
npm test
```

打包会从 `plugin/relay-native/mcp.example.json` 生成适合当前检出目录的原生 MCP 配置。首次运行真实模型前，使用自己的 Codex ChatGPT 登录，并在本机配置自己的 DeepSeek API 凭证和 Harness SDK；下文提供配置与安装步骤。

仓库不包含本机 `.relay/` 配置、密钥、会话、虚拟环境、构建结果、未经整理的本机截图和 Windows-MCP 独立项目。README 中的演示截图位于 `docs/screenshots/`，随文档提交。生成的 MCP 配置不提交，避免把开发者的绝对路径带到其他电脑。

## 推荐使用：Codex 原生插件入口

本地插件名为 `relay-native`，显示名为「异智能体合作」，声明两个原生入口：

- **全局入口「异智能体合作」**：从 Codex 侧栏打开插件应用，显示插件自身的 Codex 与 DeepSeek 两个对话窗口，可以拖动中间分隔条调整比例。
- **对话侧面板「异智能体」**：在当前 Codex 对话旁打开所选工作者，可以在团队中的 Codex、DeepSeek 实例之间切换。左侧继续使用原生 Codex 对话及其工作界面；面板可以由宿主关闭后再次打开。

插件通过 MCP Apps 加载内联前端资源，并通过本地 MCP 工具访问协作服务。原生入口不依赖在网页里绘制侧栏图标，也不以嵌套 iframe 加载本机网页。界面刷新不请求推理模型；发送消息或运行真实协作才会发生相应的模型调用。

## 多智能体与思考程度

点击顶部人数按钮管理 2–8 个实例。每个实例独立保存名称、职责、提供方、内部模型、思考程度、会话和隐藏状态。主页面保持监工与一个选中的工作者两栏，通过选择器切换工作者，不随实例数量增加列数。

隐藏聊天只改变视图，后台任务继续；管理界面和协作状态条保留停止、暂停和错误入口。切换实例或隐藏后恢复不会丢失未发送草稿。切换提供方、模型或思考程度会保存旧会话，并为该实例开始新会话；运行中由后端拒绝这些变更。

思考程度来自模型目录与适配器能力。Codex 将所选值传入真实 `turn/start.effort`；DeepSeek Harness 支持已确认的 `off/low/high/max`，对应关闭、低、高和最高，不把 Codex 的其他值静默转换过去。选择默认会沿用提供方、本机或环境配置；模型目录的默认值不是本机配置的保证值。

目前渠道是 Codex 与 DeepSeek Harness，可同时管理同渠道不同模型的多个实例，也可由任意团队成员接任后台监工。未知模型或不支持的思考选项会明确拒绝。

## 只读并行与写入执行

在团队卡中点击「展开」，选择工作方式后保存：

- **只读分析 · 可并行**：适合分析文件、检查资料、复核交付。提供方收到实际只读 policy，不能只靠提示词保证。默认允许 3 个只读执行，可在「恢复与进度」中调整为 1–4。
- **修改文件 · 独占目录**：等待其他执行退出后运行，不能与另一个写入者或读者同时访问同一个工作空间。已就绪的写入任务优先，避免持续新增读者导致它一直等待。

规划与核查始终强制只读；实际运行数来自调度 token，不按智能体的配置值猜测。默认设置保留原有实例的可写权限，需由用户明确把分析类工作者改为只读。修改工作方式与修改模型一样会归档旧会话。

收到停止请求后，界面显示停止中，直到模型进程退出且进程树清理确认后才释放执行名额。清理无法确认时会阻止后续执行，锁会跨重启保留；本版不提供没有依据的强制放行。普通聊天与自动工作流继续分开运行；独立只读聊天也遵守同一个并行上限。

当前没有给写入者建立独立 Git 工作树，所以不支持多个模型同时修改同一目录。并行修改与合并仍是后续工作。

## 核查错误与工作者返工（v0.5.1）

| 情况 | 调度行为 |
| --- | --- |
| 核查 JSON、逐项验收结果或补充分工无效 | 保留原输出、条件与证据、返工反馈和工作者尝试次数，任务仍为 `reviewing`；只重新核查 |
| 监工调用失败 | 保留交付并阻塞，检查渠道后可只重新核查 |
| 核查上限、监工预算或提供方预算耗尽 | 停止后续核查，保留未验收结果，调整对应上限或预算后继续 |
| 有效且有逐项证据的 `rejected` | 按原返工上限让工作者修正实际交付 |

`settings.maxReviewRetries` 默认 1，范围 0–10；这是首次核查之外的额外次数。`task.reviewAttempts` 持久记录当前交付已经启动的核查总次数，包含预留后被取消的核查。暂停、继续、换监工、切换合作模式与服务恢复都不减少次数；只有真正启动下一次工作者尝试、产生新交付时才归零。核查仍消耗既有监工及提供方预算，不产生独立免费调用池。

`task.reviewError` 保存最近诊断，原始无效核查回复保留在消息中。结构无效不会覆盖 `task.feedback` 或将条件改为 failed，不能把监工输出错误当成工作者不达标。界面的「待重新核查」入口按需出现，在「恢复与进度」中可调整上限与仅重新核查。

## 恢复与进度（v0.5.2）

暂停或阻塞时，顶栏的「恢复与进度」先打开只读诊断。面板展示当前目标的 `accepted`、`reviewing`、`queued`、`rejected`、`running`、`cancelled` 六种任务状态数量，最近通过的任务，以及每项任务的下一动作、工作者尝试次数、核查次数、已有输出和中断标记。最近通过记录限定为当前目标，缺少有效事件时不编造时间。

`getState()` 在返回的状态副本上附加 `recovery.summary`，由纯函数读取任务、设置、用量和执行状态生成，不把诊断持久保存。摘要以结构化 `globalIssues`、`steps[].issues` 和 `settingKey` 提供原因与设置定位，前端不解析中文错误猜测原因。读取状态、打开面板与定位字段都不会派单、增加状态修订号或重置调用计数。

诊断按真实调度顺序检查当前下一动作：核查已有交付使用监工和监工提供方预算，派工使用工作者和实际执行提供方预算，空任务图的规划使用监工预算。已通过或已取消任务不附加无关预算提示；工作者预算耗尽不会阻止核查已有输出。任务依赖、返工次数及核查上限也按下一动作判断。普通停止过程、普通聊天仍在生成、未确认的执行清理、保存失败、非合作模式和空目标分别给出结构化提示。

`summary.resume.allowed` 只代表结构条件允许继续。真实模式的继续操作仍由服务重新检查实际所需渠道，不能把页面首次读取的能力结果当成执行保证。旧服务没有恢复摘要时，界面显示待同步并禁用继续。已通过任务保留结果，`reviewing` 复用同一交付核查；曾启动后回到 `queued` 的任务可能重新执行，次数保留。这里按任务状态恢复，不提供代码中断位置的精确续跑。

等待核查但没有 `reviewError` 的任务也提供「核查已有交付」，可以手动核查或打开自动核查。原有错误任务的「仅重新核查」入口保留。手动核查在预留调用前检查实际监工渠道，其他工作者的无关渠道不会阻断；渠道失败不增加核查或调用次数。核查通过后，开启 `autoDispatch` 时可继续下游分工。

「预算与返工上限」按需展开，可从诊断提示聚焦对应字段：

| 设置 | 范围 | 含义 |
| --- | --- | --- |
| `maxSupervisorCalls` | 1–2000 | 监工自动调用上限，显示已用自动调用数 |
| `maxWorkerCalls` | 1–2000 | 工作者自动调用上限，显示已用自动调用数 |
| `maxProviderCalls.codex` / `.deepseek` | 1–2000 | 各提供方自动调用上限，显示已用自动调用数 |
| `maxRetries` | 0–20 | 首次执行之外的工作者返工次数 |
| `maxReviewRetries` | 0–10 | 每份交付首次核查之外的额外核查次数 |

调整上限会保留已用次数，不自动提高预算。普通聊天另计总调用数；这些上限无法换算成精确订阅额度。只读并行上限仍为 1–4。

保存失败时，`retrySave` 只重试保存当前状态，不启动模型或后续调度；保存成功后仍保持暂停，由用户选择何时继续。它不释放执行清理屏障。`pendingCleanup` 表示适配器尚未确认实际清理，跨重启保留，本版没有清锁、重置或强制继续接口。看到暂停或保存成功，也不能据此认定所有执行已退出。

## 原生主聊天直接委托

原生 Codex 主聊天可使用 `agent_team_status` 查看现有团队，再用 `delegate_agent_task` 把任务与验收条件交给现有非负责人工作者。工具只启动指定工作者，不额外创建后台 Codex 规划或审核调用；原生主聊天收到公开结果后负责核查、返工或下一项派单。

独立委托默认等待 30 秒，最多等待 45 秒；未完成时返回会话和消息引用，可以继续等待同一条结果。结果始终标为未验收，不能把工具完成误当成验收通过。会话或监工在提交期间发生变化时，后端会原子拒绝，避免消耗额度后才发现目标已更换。

这条路径与后台自动合作分开运行：自动合作正在执行时拒绝混用独立委托；工具不会自行切换模式、重置预算或确认完成。它按手动聊天计入提供方总调用数，自动预算单独统计。工作目录以工具返回的配置目录为准，尚未自动跟随所有宿主项目切换。

例如，可在原生主聊天明确要求：“先查看团队，把实现交给 DeepSeek，按这些验收条件核查，未通过就给反馈后继续；保留需要我决定的问题。”本机保存的提供方配置和任务授权仍然适用。

## 合作与非合作

### 任务委托书（v0.5.0）

合作监工输入区先打开任务委托书，不再直接开始后台执行。委托书包含目标、交付物、验收标准、约束和待决定问题。前三项是启动必填项；待决定问题仍有内容时，应先补齐答案或把已经决定的假设写入约束，再预览确认。

保存草稿不调用模型，也不取消或修改当前活动任务。草稿单独持久保存，确认时按已保存版本启动，活动任务使用确认快照。另一个窗口保存了更新版本时，旧预览不能派单，应重新载入最新草稿。关闭窗口会保留当前界面里的未保存编辑；服务重启后可恢复已经保存的草稿。

预览会显示当前运行模式、监工、实际工作目录和自动调用上限。「确认并开始协作」才会进入规划、派单与验收。暂停后继续原任务仍沿用原目标与产物，不需要重新提交委托书。这一版提供目标整理和确认入口；多轮自动启发与提问的需求教练尚未实现。

后台新增 `saveGoalBrief` 与 `confirmGoalBrief` 操作。新版界面在确认时同时提交预览的提供方、模型和思考程度，后台会拒绝同一监工配置已经变化的旧预览；较早客户端仍兼容不传这项配置快照。原有 `goal`、`cooperativeGoal`、`start` 等接口保留兼容；任务委托书确认是新版界面的产品流程，不能作为安全权限边界。

顶栏中的「合作／非合作」控制是否允许后台分工，和设置中的「演示／真实对话」是两个独立选项。

| 选项 | 发送消息后的行为 |
| --- | --- |
| 非合作 | 两侧各自聊天；不会自动派单、核查或返工。服务端也会拒绝启动这些协作操作。 |
| 合作 | 给当前监工输入目标时，先整理任务委托书；保存、预览并确认后启动后台规划、派单、验收与必要的修正。 |
| 演示 | 使用明确标记的模拟输出，不调用模型，不执行生成内容。 |
| 真实对话 | 使用本机 Codex 登录与 DeepSeek Harness 配置，可能消耗订阅额度和 API 用量。 |

仅切换到「合作」或保存草稿不会立即调用模型。真实合作检查实际参与团队成员的渠道；全 Codex 或全 DeepSeek 团队也可运行。在「恢复与进度」中可选择任意成员担任监工，并控制自动核查、继续分工和提供方自动调用上限。

切回「非合作」会取消正在运行的协作流程并暂停后台调度，保留已有产物、状态和用量记录；两侧普通聊天仍可继续。已经发生的模型用量或文件修改不会因切换而撤销。运行中的监工输入区提供停止按钮，对应暂停本轮协作。

## 两侧模型选择

每侧标题区分别提供自己的模型下拉框：Codex 的目录来自本机 `model/list`，DeepSeek 的目录来自已配置 API 渠道。无需通过切换另一侧来改变本侧模型。

- 切换模型会新建该侧聊天，原记录保留在该侧历史中。
- 当前模型正在回复或执行任务时，下拉框会禁用；先结束或停止工作再切换。
- 「当前默认模型」沿用该提供方的默认配置。目录可读取不代表每个模型的远端权限和真实执行都已逐一验证。
- 插件内 Codex 的模型选择只影响插件管理的 Codex 智能体，不会替换宿主当前原生主聊天的模型。

## 构建、安装与更新

需要 Node.js 22 或更新版本，以及已安装的 Codex 桌面应用。首次安装项目依赖：

```powershell
npm install
```

构建原生插件包并通过本机 Codex 插件机制安装：

```powershell
npm run package:plugin
npm run install:plugin
```

本地市场定义在 `plugin/.agents/plugins/marketplace.json`，插件包位于 `plugin/relay-native/`。安装脚本使用本机 Codex 的插件接口，不发起模型推理。前端修改后应重新打包并安装；单独更新网页构建不会自动更新已安装插件的资源副本。

安装完成后，在桌面应用中重新打开对应入口；必要时重启 Codex，使其重新读取插件工具与资源。插件可以按项目配置自动启动本地协作服务，也可手动启动：

```powershell
npm start
```

服务仅绑定本机。前端或服务端测试通过不等于桌面入口已完成视觉验收；实际检查应包括打开、关闭、再次打开，以及全局和对话侧面板的分别使用。

更新到 v0.5.3 时，应先停止 v0.5.2 及更早的后台，再启动当前项目服务。原生插件保留 `ui://relay/v0.5.2/workspace`、`ui://relay/v0.5.2/panel` 及更早资源别名，供宿主缓存的旧入口读取当前资源；这不代表没有服务标记的旧后台仍可使用。更新插件后还需要重启后台，使实际运行的服务提供新协议信息。

## 后台启动、关闭与服务识别（v0.5.3）

`createAppServer()` 自行管理的协作引擎在 HTTP 端口绑定成功后才创建和恢复状态。同端口多进程竞争时，收到 `EADDRINUSE` 的实例不会创建引擎，也不读取或写入持久快照，避免失败启动把正在运行的实例状态覆盖为另一份恢复状态。

`close()` 幂等返回同一个可等待的 Promise，停止接收新工作并结束 SSE，再等待 HTTP 服务关闭、执行清理及保存结果。关闭后的 SSE 订阅与心跳不再向已结束的响应写入。引擎在异步渠道或模型预检、保存完成后重新检查关闭状态，迟到结果不能继续修改已关闭快照或重新发起模型调用。执行清理或保存无法确认时，关闭结果报告失败并保留已有屏障，不把发出停止信号当作实际退出。

`GET /api/context` 提供以下字段：

| 字段 | 当前值或要求 |
| --- | --- |
| `service` | `relay-agent-workbench` |
| `protocolVersion` | 整数 `1` |
| `workspace` | 实际工作目录，非空字符串 |
| `version` | 当前发布版本 `0.5.3`，非空字符串 |

插件读取并验证这些字段，再访问限定的业务接口。兼容性按 `protocolVersion` 判断，因此未来发布版本不同但仍使用协议 1 的后台可以继续连接；缺少标记的旧后台、其他服务或不兼容协议会得到明确提示，不向它们发送任务，也不自动启动服务争抢端口。已收到 HTTP 响应但 JSON 无效或响应体无法读取时，同样拒绝；仅连接请求失败时尝试自动启动。插件只返回自己构造的稳定诊断，不直接透传连接或启动异常中的原始错误内容。

同一 MCP 实例内，并发请求共享完整的初始探测、启动与就绪轮询，完成或失败后清除这次在途记录。后续请求重新核实实际服务，不长期缓存就绪结论。默认启动将已经验证的本机 HTTP 地址的主机和端口传给服务，避免配置不同端口时仍启动默认端口。自动启动沿用原有项目入口与权限，不扩展到远程地址。

这套标记用于检测误连，**不等于服务身份认证**。不同 MCP 进程仍可能各自发起启动尝试，同端口竞争失败的实例通过先绑定再恢复状态保护已有快照；它不提供全局单启动保证。目前没有跨端口共用同一状态文件的进程锁，一个项目应只运行一个后台实例。

## 原生主聊天任务书桥接（v0.6.0）

`get_task_brief` 是公共只读工具，返回保存草稿的五字段、草稿版本、时间、协作会话 ID、工作目录、模式和负责人摘要，并列出缺项与待决定问题。返回值不含活动目标、任务输出、聊天记录、用量、设置或原始错误正文。读取不会启动模型。

`save_task_brief` 接收五个文本字段、`expectedStateId` 和 `expectedRevision`，只提交一次 `saveGoalBrief`。会话 ID 和草稿版本在后台原子核对，防止陈旧内容覆盖另一个保存版本或另一份协作状态；旧界面不传会话 ID 的保存方式仍兼容。五字段上限依次为 3000/3000/3000/2000/1000，总长上限 12000，拒绝额外动作和路由参数。保存草稿不会改活动目标、任务、模式或调用计数；新公共工具不提供确认及执行入口。

保存成功仅依据本次 POST 的回执：会话 ID、五字段原文和新版本必须匹配，且不能带已确认标记。409 返回最新保存版与差异字段，交由用户核对；503、响应丢失或回执不匹配返回 `unknown`，草稿可能已保存，先读取核对，不能自动重发。后续 GET 不会被当作本次提交的成功回执。协议兼容仍按版本 1 判断，保留 0.5.3 及更早 UI 资源别名。

任务书中的整理请求默认折叠，包含当前本地想法。复制后由用户在原生主聊天发送，模型先追问关键问题，再调用公共工具保存草稿；讨论使用当前聊天模型，读取和保存本身不调用推理。面板检测到保存版更新时保留本地编辑，重新载入前提供备份，预览仍按原有条件由用户确认。剪贴板不可用时可手动复制显示的请求。插件没有在后台自动开启教练对话，当前通路的实际讨论质量需要分别评估。

## 原 Codex 功能与当前边界

- 项目栏、原生标签页、预览、定时任务、新建任务和原生主聊天继续由 Codex 宿主提供。打开插件不会把这些功能替换为独立网页上的相似按钮。
- 全局插件应用中的 Codex 是插件管理的独立会话，可使用其 harness 提供的文件读写、命令、Skills 与可发现的 MCP 工具，仍受工作区和审批策略约束。它不等于宿主当前已打开的主聊天，也不包含官方桌面全部编辑器或授权界面。
- 对话侧面板显示所选工作者。后台自动规划和验收仍使用插件管理的独立监工会话；原生主聊天可通过委托工具直接指挥工作者，收到结果后自行核查。两条路径的上下文与计量不同，打开面板本身不会替换负责人。
- 切换团队监工改变后台协作的分配和验收职责，不会改变原生主聊天的模型。插件输入区、后台协作和宿主主聊天具有各自的上下文。
- 模型调用次数和 API 用量不能直接换算为精确的 ChatGPT 订阅额度节省。是否节省需要在质量验收一致的真实任务上比较。
